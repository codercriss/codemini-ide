# Security Policy

## Reporting a vulnerability

Please do **not** open a public issue for security problems.
Use GitHub's private reporting instead: **Security tab > Report a vulnerability** on this repository.
If that is unavailable, email **codercriss@gmail.com** with the subject line "CodeMini security".

Include what you found, how to reproduce it, and the browser/OS you tested on.
You will get an acknowledgement as soon as the maintainer can respond.

## Scope notes

- CodeMini runs entirely in the browser. Files and settings are stored locally in IndexedDB / `localStorage` on the user's device.
- **Locked files and folders** never store their password. A lock is a random salt plus a PBKDF2-SHA256 verifier (600,000 rounds); a locked file's text is encrypted at rest with AES-256-GCM using a key derived from that password and is only decrypted in memory after the right password is entered. File names, sizes and timestamps are not encrypted, and the contents of a locked folder are not encrypted individually. Locks created before this was added kept the password in plain text; they are upgraded automatically on load. Raw and zip downloads skip locked files, and the JSON export keeps them encrypted.
- **GitHub tokens** are encrypted with the device key (next bullet) and stored as ciphertext in `localStorage` (`codemini_git_gh_tokenenc_<window>`), so they work without a password prompt and stay usable while My Keys is locked. Older copies move over by themselves: a plain-text token the next time the page loads, a token in My Keys (where the previous version kept it) the next time My Keys is unlocked, after which the vault copy is removed. If the browser cannot keep a device key (no IndexedDB), the token goes into the My Keys vault instead and needs it unlocked. While the page is open the decrypted token is held in memory (Git operations need it immediately); it is never written anywhere in plain text.
- **The device key** (CodeMini Shield, `js/core/shield.js`) is for secrets that have no password of their own. It is one AES-256-GCM key created with `extractable: false` and kept in IndexedDB (`codemini_shield`), shared by all CodeMini windows and profiles in that browser profile. The browser will not hand out its bytes, even to code in the page. Every record is bound to what it is for (the token record to its window) and padded, so a copied record does not open elsewhere and its length does not show the token's. **It protects against:** a copy of the site's storage, a disk image, a backup or sync leak, or anyone who only gets to read the ciphertext. **It does not protect against:** someone using this open browser profile, or any script running in the CodeMini page (code you run in Normal mode, or after a fallback, runs in that page; with Isolation on, previews, the Console, the Terminal, the editor's Run and Debug and notebooks run on the runner's origin instead, see the last two bullets), because either can ask the browser to decrypt with the key. That is why it is not used for anything a password should guard: locked files, locked folders and My Keys never use it. Use a fine-grained token with the fewest scopes. Factory Reset, Wipe Native Data and Delete Profile remove a window's token record but leave the device key (it is shared, and protects nothing once the records are gone); clearing the site's data in the browser removes both. If the key is lost while the record remains (for example only IndexedDB was cleared), the token cannot be recovered: CodeMini removes the unreadable record, says so, and asks for the token again. Reports about the device key are welcome through the process above.
- GitHub integration sends requests directly from the browser to `api.github.com` with the user's own token. Tokens are never sent anywhere else.
- **My Keys** encrypts everything at rest (AES-256-GCM, PBKDF2-SHA256 with 600,000 rounds) and keeps the key in memory only while unlocked. With Isolation on (the default), previews and the code you run in the Console, Terminal, editor and notebooks run on the runner's origin and cannot reach the vault. In Normal mode, or after a fallback, that code runs in the same page as the app and is not isolated from an unlocked vault; the vault says so in its Config tab. Reports about the vault's design or implementation are welcome through the process above.
- Third-party libraries are loaded from public CDNs (see `THIRD_PARTY_NOTICES.md`).
- **Untrusted text and HTML.** The whole app runs in one origin, so a name or snippet that turns into HTML can take the app over. File, folder, archive-entry, workspace, tab and repo names, error messages, and anything a previewed page reports to the app are treated as hostile. They reach the page only through `CodeMiniEscape.html` (`js/core/html-escape.js`), `textContent` or `setAttribute`. HTML that is *meant* to be markup but comes from a file (Markdown cells and READMEs, documents, saved terminal output) goes through `CodeMiniEscape.sanitize`, an allowlist: no script, style, iframe, object, embed, svg, math or form controls, no event handlers, `id` or `name`, no `javascript:` or non-image `data:` URLs, and links get `rel="noopener noreferrer"`. Values placed inside an inline `onclick` are JSON-quoted and then escaped, because HTML-escaping alone is undone before the JavaScript runs. `tests/e2e/xss-names.e2e.js` and `tests/e2e/sanitize.e2e.js` check this in a real browser, and `tests/html-sinks.test.js` fails if any file gains a new unescaped HTML interpolation (`node scripts/scan-html-sinks.js` lists them). **Limits:** the scanner is a review aid, not a proof, and a baseline of not-yet-reviewed interpolations remains (`tests/fixtures/html-sinks-baseline.json`; most are class names, ids and numbers). The sanitizer drops `id` and `name`, so in-page anchors inside Markdown do not work.
- **Third-party scripts.** Monaco, sql.js, Pyodide and two icon stylesheets load from CDNs with pinned versions. A compromised CDN file would run with full access to the page, so `scripts/sri.js` adds (or `--check`s) Subresource Integrity hashes in `index.html`; it needs network access and has to be run by the maintainer, and until it has been, `tests/hardening.test.js` only stops *new* unprotected third-party tags. SRI does not cover files those libraries fetch later (Monaco modules, WebAssembly, Pyodide packages); self-hosting them would. The runner's execution host loads its own engines at run time (Pyodide, sql.js, Opal, php-wasm and webR, all at pinned versions: webR is pinned to release `v0.6.0`, in the runner and in the app) with no SRI. The R packages that webR downloads when you use `library(x)` come from webR's public package repository and are not pinned. A compromised engine file there would run on the runner's origin, not in the app, but it would see the code and data of every Console, Terminal and notebook run in that browser. `shield.js` is the first script on the page so no other script can replace the crypto functions it captures; a test pins that.
- **Previews run on a separate origin.** Live Preview loads a small page from the preview runner (`runner/`, deployed as its own site, `https://codemini-runner.vercel.app`) and the previewed page runs inside it. The browser's same-origin rules then keep that page away from this app's `localStorage`, IndexedDB (workspaces, the device key), cookies and functions; it cannot call `window.top.CodeMiniShield`, read the vault ciphertext or the token record, or fetch the app's files. The runner mints the `blob:` URLs the page loads (a blob URL only works for pages of the origin that made it) and relays console, network, inspector and reload messages. It holds no secrets. Only the app's own origin may embed it (`frame-ancestors`, plus an allowlist and a handshake inside the page); control messages carry a per-frame nonce; messages from the page are wrapped and treated as untrusted data; the app accepts a runner URL only if it is not its own origin. The toolbar shield shows the state (green: isolated; amber: not isolated). **Limits:** (1) If the runner cannot be reached (offline, blocked, not deployed) or you choose Normal mode (Settings > Security > Isolation: a global Isolated/Normal choice, Isolated by default, plus a per-surface override (Use global, Isolated or Normal) for Live Preview, Console, Terminal and Notebooks; `localStorage` `codemini_runner` = `off` forces Normal everywhere), previews fall back to the old same-origin mode, with the amber warning; in that mode a previewed page can read this site's storage and call the app's functions. (2) Code run from the Console, Terminal, editor and notebooks is covered by the last bullet, not this one. (3) All isolated previews share the runner's origin, so one previewed project can read what another stored there (per-project subdomains would fix that). (4) A previewed page can still run code, use the network, and read the project files it was given; Workspace Trust remains the guard for opening untrusted projects. (5) Pop-out ("open in a new tab") opens a runner page of its own, so a popped-out page is still isolated: the runner re-makes the page's files inside the new window, and the window's link back to the app (`window.opener`) is removed. (5b) Data a previewed page stores (localStorage, sessionStorage, IndexedDB) lives in the runner's origin, which the app cannot reach, so Factory Reset and Delete Profile ask the runner to clear it too (through a hidden frame if no preview is open); if the runner cannot be reached at that moment, that data is not cleared until the next reset or until you clear the site's data for the runner. (6) The runner is a trusted component: if its site were compromised, previews would be compromised (but still not the app, which treats everything from it as untrusted data). It was tested in Chromium; browsers that partition or block storage for cross-site frames were not tested and fall back if the handshake fails.
- No Content-Security-Policy is set, deliberately: previews are `blob:` and `srcdoc` documents that inherit the page's policy, so a policy strict enough to matter would break users' own pages. `<meta name="referrer">` is set to `strict-origin-when-cross-origin`.
- **CI** runs with read-only repository permissions and Dependabot watches the Actions and npm dependencies. Pinning the Actions to commit SHAs is a one-off step that needs network access (for example `npx pin-github-action .github/workflows/ci.yml`).
- **Code you run: Console, Terminal, editor and notebooks.** With Isolation on for the surface (Settings > Security; the default through the global mode), the code you run executes in a hidden frame on the runner's origin (`runner/exec.html`), one per window, and not in the app. That covers the Console's JavaScript, Python, PHP and Ruby; the editor's Run button, the bottom Console's input field and the editor's Debug (they follow the Console setting); the Terminal's `js`, `python -c`, `php -r`, `ruby -e` and script files; and Python, R and SQL notebook cells and their scratchpads (they follow the Notebooks setting). Python is one session per window shared by the Console, Terminal, editor and notebook cells; SQL has one database and R one environment per window. The code cannot read the app's storage or call its functions, and the host talks to the app only through `postMessage`: the app treats everything it returns as untrusted text and escapes it (HTML from Python's `display_html` is sanitized, notebook result tables are escaped field by field, plots are accepted only as validated base64), control messages carry a nonce, and only the embedding app may drive the host. The Terminal's own commands (`ls`, `cat`, `grep`, `calc`, ...) are the app's code and never run your code (`calc` only evaluates digits and arithmetic operators). The notebook formatter only parses your Python (`ast.parse` on a value handed over as data, never built into source), so it stays in the app. **Limits:** (1) The code in the host can still use the network and everything the runner's origin has, and the host shares that origin with previews, so a previewed page and a notebook can read each other's data on the runner. (2) If the host cannot be reached (offline, not deployed, an older runner without a newer language), the commands run inside the app as before, with a note; an older runner that lacks SQL or R says so in the cell instead. (3) Normal mode, chosen or reached by fallback, runs all of this in the app's origin, with access to its storage and an unlocked vault. (4) A Console, Run or notebook command that never ends is ended with Stop or Interrupt, which shut the host down and reset that window's variables for every surface that shares it; in the Terminal only closing the window ends it. A tight synchronous loop keeps the page from answering, and then Stop cannot act until it finishes. Measured on an iPhone (2026-10-28): a 20-second busy loop froze the whole app in the JavaScript Console and in the Python Console (the host shares the app's thread there); R's loop stopped cleanly because webR runs in its own Worker. PHP, Ruby and SQL behave like JavaScript and Python. Running them in Workers is planned. (5) The host's engines are not covered by SRI (see Third-party scripts); an `import()` of an ES module such as webR cannot carry an integrity hash in the browsers this runs on, so pinning the version is what is done there. (6) A runner older than the app needs (or one that says nothing about its version) is treated like an unreachable one: the code runs in the app, with a note that names the cause, because the alternative is to run it on code that lacks fixes the app relies on. The version is a number the runner states about itself, so it is a convenience for the person deploying, not a security check; the checks that matter are the allowed parent origin and the nonce. (7) What was tested: the automated browser tests run the host with stand-ins for Python, PHP, Ruby, SQL and R, and the real JavaScript engine. The real engines were checked by hand on an iPhone, in Isolated mode (and, for R plots, Normal too): the Console and Terminal (Python, PHP, Ruby, JavaScript), Python notebooks with `!pip install`, the Variables panel, Restart and Run All, SQL with BLOB values, R notebooks with plots, the editor's Debug, and Stop against yielding loops. Not exercised on a real engine: installing R packages, and Stop against a loop that never yields (see limit 4).
